## 1. このアプリは何をするか

モバイルICOCA の残高を定期的に確認し、設定した額を下回ったら
**公式 ICOCA アプリを開いてチャージ操作を補助する**。

### 1.1 やらないこと（絶対の前提）

以下は一切行わない。設計上「できない」ようにしてある。

- ICOCA の暗号解析、FeliCa セキュア領域の不正な読み書き、内部データの改変
- 決済認証の回避、3Dセキュア等の本人認証の突破
- クレジットカード情報の取得・保存
- ICOCA 公式アプリの通信の傍受・改ざん
- root 化の前提、セキュリティ機構の回避

拠り所は **Android の公開 API** と **公式 ICOCA アプリが通常提供する機能**、
そして **ユーザー自身による正規操作** の3つだけ。

### 1.2 必ずユーザーに渡す操作

以下が現れた時点で、設定に関係なく自動操作を止めてユーザーに引き渡す。

- クレジットカードの本人認証、3Dセキュア
- パスワード / 暗証番号 / 生体認証
- Android の権限ダイアログ

**認証を自動で突破しようとすることは、いかなる設定でも起きない。**

### 1.3 お金が動く唯一の箇所

決済の確定ボタンだけ。ここは既定では押さず、ユーザーに引き渡す。
設定「決済の確定まで自動で押す」を ON にしたときのみ自動で押すが、その場合も

1. 画面に**設定どおりの金額が表示されている**こと
2. 確定ボタンのラベルが**既知のものと完全一致**すること

の両方を満たさなければ押さない。片方でも欠ければ停止する。

### 2.1 パッケージ構成

| パッケージ | 責務 |
|---|---|
| `core` | ログ（タグ・機密マスク）、時刻抽象、文字列正規化、ICOCA 由来の定数 |
| `domain` | 判定ロジック。**Android SDK に一切依存しない純粋 Kotlin** |
| `data.settings` | `AppSettings` / 進行中の試行状態（DataStore） |
| `data.db` | Room（履歴・残高サンプル） |
| `data.repo` | 履歴リポジトリ、日次・月次の集計 |
| `balance` | 残高取得ソースのチェーン、残高テキスト解析、FeliCa 読み取り |
| `icoca` | ICOCA アプリの検出・起動・公開コンポーネント調査 |
| `accessibility` | ユーザー補助サービス、画面判定、安全ガード、ノード探索 |
| `monitor` | WorkManager、スケジューラ、フロー司令塔、確認 Activity |
| `notify` | 通知チャンネル・通知の組み立て |

`domain` と `core`、`ScreenClassifier`、`BalanceTextParser` は Android 非依存。
そのため Robolectric なしで JVM の Unit Test が回り、実機なしで検証できる。

### 2.2 依存性の注入

Hilt / Dagger は使わず、`ServiceLocator`（`IcocaApp` が保持する単純なシングルトン）で解決する。
KSP のプロセッサを増やしてビルドを脆くしないため。`domain` は純粋関数なので DI が要らず、
`data` 層はシングルトンが数個あるだけで足りる。

## 3. 主要な流れ

### 3.1 監視から完了まで

```
BalanceCheckWorker（定期）または「今すぐ確認」
  └─ ChargeFlowCoordinator.runCheck()
       ├─ 古い試行のタイムアウト処理
       ├─ BalanceRepository.refresh()        残高を取る
       ├─ ChargeDecisionEngine.decide()      チャージしてよいか
       │    └─ Skip なら理由を記録して終わり（Debug画面に理由が出る）
       ├─ ChargeStateMachine.detect()        試行を作る → CHARGE_DETECTED
       ├─ 履歴に DETECTED 行を挿入
       ├─ 低残高通知を出す
       └─ tryAutoStart()                     条件が揃えば通知を待たず自動起動
```

その先は起動経路によって2つに分かれる。

### 3.2 経路A — 通知をタップして始める（既定）

```
通知の「チャージ」
  └─ PendingIntent.getActivity → ChargeConfirmActivity（自アプリ・前面）
       └─ Coordinator.startCharge()
            ├─ 自動操作が有効なら先に beginSession()
            └─ IcocaLauncher.launchMain()   ここは前面なので起動が許される
```

### 3.3 経路B — 通知を待たず自動で始める

設定「チャージ前にタップして確認する」を OFF にしたときだけ通る。
`tryAutoStart()` が次の4条件をすべて満たしたときのみ動き、1つでも欠けたら
何もせず経路A に委ねる（どの条件で落ちたかは必ずログに残す）。

1. `confirmBeforeCharge` が OFF
2. 自動操作が有効かつ同意済み
3. ICOCA アプリがインストールされている
4. **ユーザー補助サービスが接続されている**

4 が最も落ちやすい。**Android は APK を再インストールするたびにユーザー補助の許可を
自動で無効化する。** 設定自体はアプリをまたいで残るため、再インストール後は
毎回ここだけが落ちる。

バックグラウンドから他アプリの Activity を起動することは通常 Android にブロックされるが、
ユーザー補助サービスはシステムにバインドされているためこの経路なら起動できる。

### 3.4 見届けと検証

`ChargeFlowService`（Foreground Service）が `superviseAndVerify()` を回す。

```
自動操作あり → セッションの決着を待つ（最大3分）
  ├─ Stopped → 失敗として履歴に記録し、エラー通知
  └─ それ以外 → CHARGING へ

90秒待つ（決済と本人認証はユーザーの操作なので待つ）
  └─ verifyNow()
       ├─ 残高が取れない          → SUCCESS_UNVERIFIED
       ├─ before + amount 以上   → SUCCESS
       ├─ before と変わらない     → FAILED(NOT_CHARGED)
       └─ それ以外               → FAILED
```

残高が取れないときに **失敗にも成功にもしない**のは意図的。
「取れなかった＝失敗」にすると、実際にはチャージ済みなのにクールダウン明けに
再チャージしてしまう恐れがあるため。

## 4. 状態機械

```
                  ┌──────────────┐
                  │     IDLE     │
                  └──────┬───────┘
     残高 < 閾値 かつ 各種条件OK │
                  ┌──────▼───────┐
                  │CHARGE_DETECTED│  通知を出した
                  └──────┬───────┘
     通知タップ / 自動起動  │
                  ┌──────▼───────┐
                  │CHARGE_PENDING │  ICOCAアプリ起動待ち
                  └──────┬───────┘
                  ┌──────▼───────┐
                  │   CHARGING    │  画面遷移 / 金額選択 / 決済
                  └──────┬───────┘
                  ┌──────▼───────┐
                  │   VERIFYING   │  残高の再取得
                  └───┬───────┬──┘
              ┌───────▼──┐ ┌──▼───────┐
              │ SUCCESS  │ │  FAILED  │
              └───────┬──┘ └──┬───────┘
                      └───┬───┘
                 クールダウン開始 → IDLE
```

遷移は `ChargeStateMachine.transition()` の一箇所でのみ行う。
許可されていない遷移は **例外を投げず `Result.Rejected` を返して現状維持**する。
自動操作の最中に例外で落ちると復旧できなくなるため。
状態は DataStore に永続化するので、プロセス終了や端末再起動をまたいでも復元される。

### 4.1 二重チャージ防止（最重要）

4段構えで防ぐ。

| # | 仕組み | 内容 |
|---|---|---|
| 1 | 非終端状態の一意性 | `IDLE`/`SUCCESS`/`FAILED` 以外の試行が存在する間、新しい試行を作らない |
| 2 | 同一残高の再観測を弾く | 試行が持つ `balanceAtDetection` と同じ残高を見ただけなら発火しない |
| 3 | クールダウン | 終端に落ちてから `minChargeIntervalHours`（既定6時間）は再発火しない。ユーザーがキャンセルした場合も同じ |
| 4 | タイムアウトで強制終端 | 進行中の試行が30分を超えたら `FAILED(TIMEOUT)` に落として state を解放する |

4 が無いと、ユーザーがチャージ途中で離脱した場合に `CHARGE_PENDING` のまま残り、
以後まったく発火しなくなる。

さらに `ChargeFlowCoordinator` は `Mutex` で直列化している。
Worker と UI が同時に走っても試行が2つ生まれることはない。

## 5. チャージ判定（`ChargeDecisionEngine`）

純粋関数。上から順に評価し、**最初に引っかかった理由をそのまま返す**。
返った理由は Debug 画面の「直近のスキップ理由」に出る。

| # | 条件 | 通らないときの理由 |
|---|---|---|
| 1 | 監視が ON | `MONITORING_DISABLED` |
| 2 | 残高が取得できている・妥当・古すぎない | `BALANCE_UNKNOWN` |
| 3 | `残高 < 閾値`（ちょうど閾値では発火しない） | `ABOVE_THRESHOLD` |
| 4 | 進行中の試行がない | `ATTEMPT_IN_PROGRESS` |
| 5 | 前回終端からクールダウン経過 | `COOLDOWN` |
| 6 | チャージ額 ≤ 20,000（ICOCA 1回上限） | `EXCEEDS_PER_CHARGE_CAP` |
| 7 | 当日合計 + 金額 ≤ 日次上限 | `DAILY_LIMIT` |
| 8 | 当月合計 + 金額 ≤ 月次上限 | `MONTHLY_LIMIT` |
| 9 | 残高 + 金額 ≤ 20,000（ICOCA 残高上限） | `WOULD_EXCEED_CARD_CAP` |
| 10 | メンテナンス時間帯（2:00–4:00 JST）でない | `MAINTENANCE_WINDOW` |
| 11 | Wi-Fi 条件（設定時） | `REQUIRES_WIFI` |
| 12 | 充電中条件（設定時） | `REQUIRES_CHARGING` |

日次・月次の集計は **Asia/Tokyo のカレンダー日 / 月**で行う（`LimitCalculator`）。
集計対象は `SUCCESS` と `SUCCESS_UNVERIFIED`。裏取りできていない分も安全側で数える。

### 5.1 ICOCA 由来の定数（`IcocaConstants`）

アプリの設定では変更できない。JR西日本の仕様だから。

- カード内残額上限: 20,000円
- 1回のチャージ上限: 20,000円
- メンテナンス時間帯: 2:00–4:00（日本時間）
- ICOCA アプリのパッケージ: `jp.co.westjr.android.icocaapp`

## 6. 残高の取得

### 6.1 取得チェーン（`BalanceRepository`）

`BalanceSource` を優先度順に試し、**最初に成功したものを採用**する。
どれも失敗したら `null` を返す。**推測値は決して返さない。**

| 優先度 | 実装 | 状態 |
|---|---|---|
| -1 | `SimulatedBalanceSource` | Debug 画面の疑似値。明示設定時のみ成立し、1回使うと消える。リリースビルドの UI からは到達できない |
| 0 | （公式 API） | 存在しないため未実装 |
| 1 | `IntentBalanceSource` | **スタブ**。公開 Intent が無いため常に `null`。見つかったらここに実装を足す拡張点 |
| 2 | （NFC） | チェーンには入れない（次項） |
| 3 | `AccessibilityBalanceSource` | ICOCA アプリが前面のとき、画面テキストから抽出 |
| 4 | `ManualBalanceSource` | 手入力値 / NFC 読み取り値。常に成立する Fallback |

疑似値を最優先にしてあるのは、直前にユーザー補助が読んだ実残高に負けると
低残高テストが実質できなくなるため。1回で消費されるので実害はない。

### 6.2 NFC をチェーンに入れない理由

物理カードの読み取りはユーザーが端末にカードをかざして初めて成立するので、
バックグラウンドのチェーンから呼べる形にならない。
`FelicaBalanceReader` を `MainActivity` のリーダーモードから使い、
読めた値をチェーンの外から流し込む。

**読めるのはかざした物理 ICOCA カードだけで、自端末のモバイルICOCA は読めない。**
内蔵 SE は OS が保護しており、OMAPI も GlobalPlatform の SE Access Control に阻まれる。

### 6.3 鮮度

読み取り結果は `observedAt` を持ち、`BalanceReading.isStale(maxAge)` で古すぎる値を弾く。
既定の最大鮮度は24時間。手入力値は「乗車すれば減る」ので過信しない設計。

## 7. 残高テキストの解析（`BalanceTextParser`）

**誤検知が最も危険**なので保守的に作る。

- 受理する形: `¥2,840` / `2,840円` / `残高 2,840` / `2840` / 全角
- ラベル: `残高` `残額` `ざんだか` `SF残` `チャージ残` `現在の残`
- 候補ごとにスコアを付け、`MIN_SCORE`（3）に届かなければ採用しない

スコアの考え方:

| 手がかり | 加点 |
|---|---|
| 同じノードにラベルがある | +4（単独で採用に足りる） |
| 前後2行以内にラベルがある | +3 |
| 通貨記号がある | +1 |
| 桁区切りのカンマがある | +1 |
| 100未満の小さい数 | −2 |

さらに次を除外する。

- `23:34` のような時刻
- **「チャージ後の残額」などの予定額**（`チャージ後` `後の残` `変更後` `予定`）

ラベルは数値の**前にも後ろにも**現れうるため、両方向を見る。
これは実機のメイン画面が「円 / 6,271 / チャージ残額」という並びだったことから分かった（§13）。

## 8. 自動操作（`AutomationEngine`）

ユーザーが Android 設定から明示的に有効化したときだけ動く。
`accessibility_service_config.xml` で監視対象を ICOCA アプリのみに限定している。

- `packageNames="jp.co.westjr.android.icocaapp"` — 他のアプリの画面は一切見ない
- `canPerformGestures` は宣言しない — 座標タップを行わないため
- `isAccessibilityTool="false"` — 本アプリは障がい支援ツールではない（Google Play ポリシー）

### 8.1 画面判定（`ScreenClassifier`）

座標や画面構造ではなく **テキストだけ**を見る。ICOCA アプリのレイアウト変更に強くするため。
判定順は固定で、上から順に最初に当たったものを返す。

| 順 | 画面 | 手がかり |
|---|---|---|
| 1 | `AUTHENTICATION` | 3Dセキュア / 本人認証 / パスワード / 暗証番号 / 生体認証 / セキュリティコード … |
| 2 | `ERROR` | エラー / 失敗しました / できませんでした / 通信に失敗 … |
| 3 | `COMPLETED` | 完了しました / チャージが完了 / 受け付けました |
| 4 | `PAYMENT_CONFIRM`（強） | **確認ダイアログにしか出ない語**: チャージ確認 / チャージしますか / お支払い額 / この内容で … |
| 5 | `CHARGE_AMOUNT` | 「チャージ金額」等の見出し、または1,000円単位の金額が3つ以上、または「〜でチャージ」ボタン＋金額1つ以上 |
| 6 | `CHARGE_ENTRY` | チャージ方法 / チャージ手段 / 支払い方法 |
| 7 | `PAYMENT_CONFIRM`（弱） | **金額選択画面にも出うる語**: 決済 / お支払い / 支払う |
| 8 | `PROCESSING` | 処理中 / しばらくお待ち / 通信中 |
| 9 | `MAIN` | 残高ラベルが見える |
| — | `UNKNOWN` | どれにも当たらない |

**4 と 7 を分けているのが要点。** 金額選択画面にはカードの行（「お支払い方法」など）が
載っているため、「お支払い」を確認ダイアログの証拠として扱うと金額選択画面が
`PAYMENT_CONFIRM` と誤判定され、そこで自動操作が終わってしまう（§13.4）。

確認ダイアログは金額選択画面の**上に重なって**出るので両方の文字が同時に見える。
強い語を先に見ることで、重なっている間は確認ダイアログ側として扱われる。

### 8.2 動かし方 — イベントではなく周期で見る

**AccessibilityEvent に依存しない**（改修指示 §1, §4, §5）。

以前は「イベントが来る → 画面を判定 → 1手打つ → 次のイベントを待つ」という作りで、
イベントが1回来ないだけでそこから先へ二度と進まなかった。
実機では次の2つが確実にイベントを止める。

- 「チャージ」を押した直後に挟まる、中身の出来ていない画面
- すでに 5,000 が選ばれている金額画面で 5,000 を押す（見た目が変わらない）

いまは `AutomationEngine` がフローを所有し、**300ms ごとに `rootInActiveWindow` を
取り直して**判断する。イベントの役目は「画面が変わったかもしれない」という印を
立てることだけで、分類も判定もクリックもコールバックの中では行わない。
イベントの欠落・順序の入れ替わり・重複・Compose 由来の大量発火の
どれにも影響されない。

`IcocaAccessibilityService` が持つのはループと画面の撮影だけで、判断は全部エンジンにある。

### 8.3 状態（`AutomationState`）

`ChargeState`（永続・粗い・二重チャージ防止の土台）とは**別に**、
エンジン内部の細かい状態を持つ（改修指示 §10）。

```
LAUNCHING_ICOCA → WAITING_FOR_MAIN → MAIN_READY → CLICK_CHARGE
  → WAITING_FOR_CHARGE_ENTRY → CHARGE_ENTRY
  → WAITING_FOR_AMOUNT → CHARGE_AMOUNT → SELECTING_AMOUNT
  → WAITING_FOR_PAYMENT_BUTTON → PAYMENT_READY
  → PAYMENT_CONFIRM → PROCESSING → WAITING_FOR_COMPLETION → COMPLETED
```

終わり方は `SUCCESS` / `FAILED` / `USER_ACTION_REQUIRED` の3つ。
`USER_ACTION_REQUIRED` は**失敗ではない**（本人認証や決済確認への到達）。

`ChargeState` に混ぜなかったのは、あちらが DataStore に永続化され、
遷移表と30分タイムアウトで二重チャージを防いでいるため。
細かい状態を足すと遷移表が破綻する。境界で写像するだけにしてある。

進行状況は別に `AutomationStatus` で持つ。
`RUNNING` / `WAITING` / `RECOVERING` / `USER_ACTION_REQUIRED` / `SUCCESS` / `FAILED` / `CANCELLED`。
**`WAITING` は正常**で、画面遷移中やボタン待ちはここに入る。

### 8.4 待つのか止めるのか

方針は1つ（改修指示 §23）。

> **正常な待機では止まらず、本当に異常なときだけ安全に止まる。**

| 状況 | 判断 |
|---|---|
| 画面遷移中 / イベント欠落 / 同一画面 | 継続 |
| 判別できない画面 | 原則待機（20秒まで） |
| 本人認証 | ユーザーへ引き渡し（失敗ではない） |
| 明確なエラー画面 | 停止 |
| 状態ごとの timeout 超過 | Recovery → それでも駄目なら停止 |
| 安全条件の不一致 | 即停止 |

**「同じ画面が15秒続いたら停止」は廃止した**（改修指示 §8）。
画面が変わらないこと自体は異常ではない。決済の確認ダイアログは人が読む間ずっと
同じ画面だし、通信待ちも動かない。金額を押しても既にその額なら見た目は変わらない。
どれも正常系なのに一律で切っていた。

代わりに**いま何を待っているか**で上限を決める（`AutomationTimeouts`）。

| 状態 | 上限 |
|---|---|
| `LAUNCHING_ICOCA` | 15秒 |
| `WAITING_FOR_MAIN` / `WAITING_FOR_CHARGE_ENTRY` / `WAITING_FOR_AMOUNT` / `WAITING_FOR_PAYMENT_BUTTON` | 20秒 |
| `SELECTING_AMOUNT` | 5秒 |
| `PAYMENT_CONFIRM` | 60秒（**人が読んで判断する画面**。急かさない） |
| `PROCESSING` / `WAITING_FOR_COMPLETION` | 120秒（決済の通信待ち。短く切ると成功を失敗扱いにしかねない） |

ユーザー設定にはしない。伸ばせてしまうと、UI が変わって二度と進めない状態を
延々と待ち続けることになる。

判別できない画面は**回数ではなく時間**で20秒待つ（改修指示 §7）。
何も押さないので、待っても危険は増えない。
セッション全体の最後の歯止めは5分。

### 8.5 Recovery

上限を超えたらまず `RECOVERING` に移り、**現在画面を取り直して状態を引き直す**
（改修指示 §16）。想定と違う画面にいても、いまどこにいるか分かるならそこへ合わせる。

状態の引き直しには向きの規則がある。

- **前に進む向き**（画面のほうが先に行っている）→ いつでも合わせる。
  途中の画面が出ずに飛ばされるのは実機でも普通
- **戻る向き** → `RECOVERING` のときだけ。
  ボタンを押した直後は画面がまだ前のままなのが当たり前で、ここで引き戻すと
  「押す → 戻される → また押す」を周期ごとに繰り返して連打になる

Recovery でやるのは再分類だけ。**座標タップ・戻るボタン連打・HOME・
ICOCA の強制終了や無条件の再起動・ランダムクリックは一切行わない**（改修指示 §17）。
15秒粘っても戻らなければ停止する。

### 8.6 連打を防ぐ（`ActionThrottle`）

300ms ごとに画面を見るが、**見るたびに押してよいわけではない**（改修指示 §6）。
素直に実装すると1秒に3回同じボタンを叩く。決済が絡む画面でそれは論外。

2段構えで止める。

1. **同一ステップでの再クリック禁止** — 一度押したノードは状態が進むまで押さない
2. **クールダウン 800ms** — 状態が進んで同じノードに戻ってきても、間隔を空ける

同一性は「画面種別 + ノード識別子 + 操作種別」の3つ組で見る。
ノード識別子は `viewId` → ラベル → クラス名の順で決める。

### 8.6.1 ボタンの掴み方（`NodeFinder`）

**座標は一切扱わない。** text / contentDescription / viewIdResourceName だけを見る。

**見た目のボタンと `AccessibilityNodeInfo` の構造は一致しない。**
実機で「****9804でチャージ」が見えているのに押されない、ということが起きた。
固定文字列での完全一致は使わない。

照合の前に `TextNormalizer` で揃える。

- 前後の空白を落とす / 連続空白と改行を除去
- 全角と半角を吸収（`＊＊＊＊９８０４` も `****9804` も同じに見える）
- 通貨記号とカンマのゆれを吸収

そのうえで、可変部分（カード番号）を避けて **「でチャージ」** だけを手がかりに、
確からしい順で探す。

| 順 | 探し方 | 拾えるもの |
|---|---|---|
| 1 | ノード自身のテキストが語で**終わる** | `****9804でチャージ` |
| 2 | ノード自身のテキストが語を**含む** | `****9804でチャージする` |
| 3 | 子孫テキストを連結して語を含む | `****9804` と `でチャージ` が別ノード |

押す相手の決め方（最大8階層）。

- **A.** 文字のノード自身が押せる（depth 0）
- **B.** 親が押せる（depth 1）
- **C.** さらに上の祖先が押せる（depth 2 以上）

**無関係な親まで上がってはいけない。** 画面全体を包むコンテナを掴むと、
まったく別の場所を叩くことになる。祖先の子孫テキストが
「照合した語をまだ含み、かつ語に対して極端に長くない」ことを確かめ、
外れたらそこで打ち切る。

押せるかどうかは `isClickable` だけでは判断しない。
独自 View や Compose には、`isClickable=false` なのに
**action list に `ACTION_CLICK` を持つ**ノードがある。逆もある。
どちらか一方でも押せるなら押せるものとして扱う。

押す直前に、何を掴んだのかを必ず記録する。

```
[PAYMENT_METHOD_BUTTON_FOUND] text= className= isClickable= isEnabled=
  actions= parent1= parent1Clickable= parent2= parent2Clickable= depth=
[PAYMENT_METHOD_BUTTON_CLICK] result=true
```

**`result=true` は「チャージ操作が成功した」ではない。**
アクセシビリティのアクションが受け付けられたというだけで、
ICOCA 側が画面を進めたかどうかは何も言っていない。
次の周期で `rootInActiveWindow` を取り直し、
画面が `PAYMENT_CONFIRM` に変わったことを見て初めて次へ進む。
古いノードは使い回さない。

支払いボタンを押した後は最大60秒、300ms ごとに
`PAYMENT_CONFIRM` / `AUTHENTICATION` / `PROCESSING` / `COMPLETED` / `ERROR` / `UNKNOWN`
を見分ける。ただし **`AUTHENTICATION` と `ERROR` の判定は `PAYMENT_CONFIRM` より先**に置く。
認証画面を決済確認と取り違えると、認証を自動で突破しにいくことになるため、
ここだけは優先順位を動かさない（§1.2）。

### 8.6.2 押すとき — 旗を信じず、試す

実機のダンプで分かったこと。**「****9804でチャージ」の正体は `ScrollView` の中の
`TextView`** であり、`Button` ではなかった。

```
ScrollView id=jp.co.westjr.android.icocaapp:...
  ViewGroup
    TextView  text=****9804でチャージ     ← これが見た目のボタン
    Button    text=10,000  click=true
    Button    text=5,000   click=true
    ...
  ImageButton desc=上へ移動               ← スクロールする画面
```

探索は成功し `[PAYMENT_METHOD_BUTTON_FOUND]` は出ていた。
**失敗していたのは `performAction` のほう**で、false が返っていた。

`isClickable` や action list は当てにならない。旗を見て諦めるのではなく、順に試す。

1. **`refresh()`** — 掴んでから押すまでにツリーが作り直されていると、
   古いノードへの `performAction` は何もせず false を返す
2. **`ACTION_SHOW_ON_SCREEN`** — スクロール領域の外にいるノードは押せない。
   画面内へ入れてからもう一度
3. **自分 → 親 → さらに上の順に、実際に `performAction` を試す。**
   無関係なコンテナまで上がらないよう、§8.6.1 の範囲判定を各段で通す

**1回の false でセッションを畳まない。** 以前はここで即中止していたため、
画面内に入れ直せば押せたものまで落としていた。押し直せるようにして次の周期に賭ける。
連打にはならない（`ActionThrottle` のクールダウン 800ms は残る）し、
無限に粘ることもない（`PAYMENT_READY` の上限20秒で区切る）。

### 8.7 金額の選び方

押した後にイベントを待たない（改修指示 §11）。
**押しても見た目が変わらないのを正常系として扱う。**

```
CHARGE_AMOUNT
  → 設定額のプリセットを探す（入力欄は除外）
  → 見つかれば1回だけ押す → SELECTING_AMOUNT
  → 見つからなくても設定額が画面に出ていれば、選び直さず次へ
  → どちらでもなければ待つ（上限に達したら Recovery）
WAITING_FOR_PAYMENT_BUTTON
  → 300ms ごとに「〜でチャージ」を探す
  → 見つかれば PAYMENT_READY → 押す
```

入力欄を除外するのは、金額選択画面の上部に編集可能な金額欄があり、
下のプリセットと同じ「5,000」が出るため。欄を押すとキーボードが出るだけで進まない。

### 8.8 決済の確定

**このアプリで唯一、お金が動く操作**（改修指示 §13）。
自動確定が OFF なら `USER_ACTION_REQUIRED` としてユーザーへ引き渡す。

ON の場合も、次が**すべて**揃わなければ押さない。

1. `packageName` が ICOCA 公式アプリ
2. 署名が初回検出時と一致
3. いまの画面が `PAYMENT_CONFIRM`
4. 画面上のチャージ金額が設定額と一致
5. 確定ボタンのラベルが既知のものと完全一致
6. `SafetyGuard` を通過
7. `ActionThrottle` を通過

1つでも欠ければ押さない。

押した後は `PROCESSING` を見込むが、ここでもイベントには依存しない（改修指示 §14）。
300ms ごとに取り直して `PROCESSING` / `COMPLETED` / `ERROR` / `AUTHENTICATION` / `UNKNOWN`
を見分ける。**`AUTHENTICATION` は即座にユーザーへ引き渡す。**

### 8.9 安全ガード（`SafetyGuard`）

`SafetyGuard` が見るのは「**そもそも触ってよい相手か**」だけになった。

| # | ガード | 通らないとき |
|---|---|---|
| 1 | 操作対象が ICOCA 公式アプリか | `PACKAGE_MISMATCH` で停止 |
| 2 | 署名が初回検出時と同一か | `SIGNATURE_MISMATCH` で停止 |
| 3 | クリック回数 ≤ 12（無限ループ防止） | `STEP_LIMIT_EXCEEDED` で停止 |

時間に関する判断（同一画面の滞留、判別できない画面の連続）は持たない。
**このクラスは時計を持っていないので、持つべきでもなかった。**
上限の管理は `AutomationTimeouts` と `AutomationEngine` に移した。

画面の意味づけも分けてある。認証画面を「停止すべき異常」として返すと、
ユーザーへの引き渡しが失敗として記録されてしまうため、
畳むか渡すかはエンジンが決める。

### 8.10 診断（実機で止まったときに追う手段）

端末では logcat を取れないため、アプリ自身に残させる。
**いずれもメモリ上にのみ保持し、永続化しない。**
ボタンのラベルにはカード番号が入りうるので、必ず `LogRedactor` を通す。

| 表示 | 内容 |
|---|---|
| 自動操作の状態 | Session ID / Attempt ID / Status / State / Screen / Step / Last Action とその時刻 / Last Screen Change / Unknown Since と継続時間 / Current Timeout / 経過時間 / ICOCA Foreground / Accessibility Connected |
| 自動操作の記録 | `SCREEN` `ACTION` `WAIT` `RECOVERY` `TIMEOUT` `USER_ACTION_REQUIRED` `SUCCESS` `FAILURE` の時系列 |
| 画面履歴 | 直近50件（時刻・画面・状態・ステップ・ノード数・主要テキスト） |

```
11:05:21 SCREEN MAIN
11:05:22 ACTION CLICK "チャージ"
11:05:22 WAIT WAITING_FOR_CHARGE_ENTRY を待機中
11:05:22 SCREEN UNKNOWN
11:05:24 SCREEN CHARGE_AMOUNT
11:05:25 ACTION CLICK "5,000"
11:05:26 ACTION CLICK "****でチャージ"
11:05:29 SCREEN PAYMENT_CONFIRM
```

## 9. バックグラウンド起動制限への対応

**やらないこと**: WorkManager から直接 `startActivity` で ICOCA を起動する（BAL でブロックされる）。

**やること**: 2つの合法な経路だけを使う。

```
経路A  通知 → PendingIntent.getActivity → 自アプリの Activity（前面）→ ICOCA 起動
経路B  ユーザー補助サービス（システムにバインドされている）→ ICOCA 起動
```

通知アクションは **`PendingIntent.getActivity` を直接使う**。
`BroadcastReceiver` を経由すると Android 12+ の通知トランポリン制限に抵触する。

`SYSTEM_ALERT_WINDOW` は宣言しない。

## 12. セキュリティとプライバシー

### 12.1 保存しないもの

カード番号 / セキュリティコード / 3Dセキュアのパスワード / ICOCA ログインパスワード / 生体認証情報。
必要な決済処理はすべて公式 ICOCA アプリに任せる。

### 12.2 ログに出さないもの

`SecureLog` が出力前に `LogRedactor` を通す。

- 12桁以上の連続数字（カード番号らしきもの） → `****`
- `password` / `pin` / `cvv` / `暗証` / `セキュリティコード` 等のキーに続く値 → `****`
- **すでにマスクされたカード番号（`****9804`）** → `****`
  （下4桁だけでは12桁の閾値に届かず素通りしていた。実機の支払いボタンのラベルが
  「****9804でチャージ」で、これが記録に載りうるため追加した）

金額（`5,000`）は潰さない。潰すと診断の役に立たなくなるため。

ログタグ: `ICOCA_MONITOR` / `ICOCA_BALANCE` / `ICOCA_AUTOMATION` / `ICOCA_PAYMENT` / `ICOCA_ERROR`

### 12.3 その他

- ユーザー補助が取得したテキストは**残高抽出と画面判定にのみ使い、永続化しない**
- **`INTERNET` 権限を宣言しない。** このアプリはネットワーク通信を一切行わない
- `allowBackup="false"` / `dataExtractionRules` で履歴の端末外流出を防ぐ

### 12.4 権限

| 権限 | 用途 |
|---|---|
| `POST_NOTIFICATIONS` | 残高低下・結果の通知 |
| `RECEIVE_BOOT_COMPLETED` | 再起動後に監視を再スケジュール |
| `ACCESS_NETWORK_STATE` | 「Wi-Fi時のみ」の判定 |
| `FOREGROUND_SERVICE` / `..._SPECIAL_USE` | フロー実行中の可視化 |
| `NFC`（任意） | 物理 ICOCA カードの残高読み取り |
| `BIND_ACCESSIBILITY_SERVICE` | 自動操作（ユーザーが設定で有効化したときのみ） |

宣言しないもの: `INTERNET` / `SYSTEM_ALERT_WINDOW` / `PACKAGE_USAGE_STATS` /
`BIND_NOTIFICATION_LISTENER_SERVICE`

## 13. 実機で判明した制約と不具合

机上では気づけず、実機のデータでしか分からなかったもの。いずれも回帰テストに固定してある。

### 13.1 残高を 6,271円 ではなく 6円 と誤読していた（重大）

メイン画面のノード列は `円 / 6,271 / チャージ残額 / 日 / 6 / 月 / 3 …`。
ラベル「チャージ残額」が数値の**後ろ**にあり、ラベルの後ろだけを見る実装では
6,271 を取り逃し、**直後に並ぶ定期券の日付「6」を残高として拾っていた。**
残高6円として閾値を割り、誤ってチャージ処理を起動する状態だった。

→ ラベルを前後両方向で探すスコア方式に変更（§7）。

### 13.2 メイン画面を金額選択画面と誤判定していた

定期券の日付（6, 3, 8）が裸の数字として並ぶため、
「金額らしき数字が3つ以上」で金額選択画面と誤判定していた。

→ 「1,000以上かつ1,000の倍数」に絞り、時刻も除外。

### 13.3 金額選択画面で永久に止まっていた（イベント待ち）

すでに「5,000」が表示されている状態で「5,000」を押しても画面の見た目が変わらないため、
次のアクセシビリティイベントが発生せず、そこで永久に止まっていた。

→ 金額選択と支払いボタンを同じイベント内で続けて押す（§8.2）。

### 13.4 金額選択画面を決済確認画面と誤判定していた

金額選択画面に載っているカードの行の「お支払い」を確認ダイアログの証拠として
扱っていたため、金額選択画面が `PAYMENT_CONFIRM` になっていた。すると

- 自動確定 OFF → その場で正常終了して止まる
- 自動確定 ON → 確定ボタンのラベルが画面に無いので何も押せず止まる

どちらの設定でも先に進めなかった。

→ 決済語を強弱2つに分け、金額選択画面を先に判定する（§8.1）。

### 13.5 遷移中の空の画面でセッションが死んでいた

「チャージ」を押した直後、ノード13個のうち文字を持つのが「更新」と時刻だけという、
**まだ中身の出来ていない画面**が一瞬挟まる。これが `UNKNOWN` と判定され、
`UNKNOWN` は即座にセッションを中止する作りだったため、
チャージ画面に着く前に毎回セッションが死んでいた。

ICOCA アプリ側は中止後も遷移を続けるので、利用者からは
「チャージ画面が出たまま自動操作が止まった」ようにしか見えなかった。
金額の設定値とは無関係に起きる。

→ 判別できない画面は「何も押さずに待つ」に変更。6回連続で中止（§8.4）。

### 13.6 イベントが来ない瞬間がある（今回の全面改修の理由）

13.3 と 13.5 は症状が違うだけで、根っこは同じだった。
**AccessibilityEvent は「必ず来る」ものではない。**

- 画面を組み立てている途中の中身の無いツリー（13.5）
- すでに選ばれている金額を押しても見た目が変わらない（13.3）

どちらも「次のイベントを待つ」設計では詰む。個別に手当てしても、
イベントが来ない瞬間がある以上は別の形で再発する。

→ イベント依存をやめ、300ms 周期で現在画面を取り直す方式に変更（§8.2）。
イベントは「変わったかもしれない」という印だけになった。

### 13.7 viewId はほぼ取得できない

ICOCA アプリのノードは `viewIdResourceName` を持たないものが大半。
したがって照合は text / contentDescription が主軸になる。

### 14.1 CI（`.github/workflows/icoca-auto-charge.yml`）

開発環境から `maven.google.com` に到達できないため、コンパイル・Unit Test・Lint は
GitHub のランナーで回す。実機検証用の APK を Release に直リンクで置く。

```
assembleDebug → testDebugUnitTest → lintDebug → Release に APK を添付
  └─ 4つのうち1つでも失敗したら最後のゲートでジョブを落とす
```

`gh release create` がタグ未作成の状態で呼ばれると draft のまま中途半端に止まり、
**CI は緑なのにダウンロードだけ 404** になる事故を実際に踏んだ。
そのためタグは明示的に push し、公開状態（タグ名と draft）を検証してから成功とする。

### 14.2 テスト

`domain` / `core` / `ScreenClassifier` / `BalanceTextParser` が Android 非依存なので、
JVM の Unit Test で判定ロジックをほぼ網羅できる。実機の画面から採取したノード列は
`RealDeviceScreenTest` に固定してあり、§13 の不具合はすべてここで再現・防止している。

**自動操作そのものも JVM から動かせる。** `AutomationEngine.tick(snapshot, now)` が
時刻を引数で受け取り、画面を `ScreenAccess` インタフェース越しに見るので、
`AccessibilityNodeInfo` はエンジンに届かない。おかげで

- イベントが1回も来ない
- 同じ画面が15秒続く
- 判別できない画面が20秒続く
- 同じボタンが何周期も見え続ける

といった、本来なら実機でしか起きない状況を `AutomationEngineTest` で再現できる。
待ち時間も実時間ではなく引数なので、20秒のテストも一瞬で終わる。

実機でしか確かめられないのは通しの流れ（起動から完了確認まで）と、
実際のノード構造がこちらの想定と合っているかの2点。手順は `TEST_PLAN.md`。

## 15. 既知の限界

- **Google Play では配布できない。** ユーザー補助を障がい支援以外の目的で使うため、
  ポリシー上 sideload 前提になる
- **Android 17 の「高度な保護モード」**を有効にすると、OS が自動操作を無効化する。
  その場合でも通知からワンタップで ICOCA を開く運用は使える
- **自端末のモバイルICOCA の残高は NFC で読めない。** 読めるのはかざした物理カードだけ
- ICOCA アプリの画面が変われば、画面判定とラベルの更新が必要になる。
  壊れたときは「止まる」側に倒れる設計にしてあるが、止まること自体は起きる
- 公式 Intent / API が提供されれば、ユーザー補助に頼らない実装に置き換えられる。
  `IntentBalanceSource` がその拡張点として空けてある
